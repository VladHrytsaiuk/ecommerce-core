# База даних та робота з міграціями (AquaWheel)

Цей документ описує загальну структуру бази даних PostgreSQL для нашого проєкту та посібник з користування інструментом для міграцій.

## Структура Бази Даних (Schema)

На даний момент база даних складається з **28 таблиць**, що об'єднані в такі логічні блоки:

### 1. Користувачі та Безпека
- **`role`**: Ролі користувачів (адмін, клієнт тощо).
- **`user`**: Центральна таблиця всієї системи. Зберігає профілі, паролі (хеші), статуси верифікації.
- **`verify_code`**: Зберігає одноразові коди (деталі для підтвердження номеру телефону/email, скидання пароля).
- **`session`**: Таблиця для керування користувацькими сесіями (зберігання `refresh_token`, прив'язка до пристроїв, відкликання токенів).
- **`user_address`**: Зберігає список адрес доставки, збережених користувачами.

### 2. Товарний Каталог (PIM)
- **`category`** та `category_translation`: Дерево категорій продуктів з підтримкою мультимовності.
- **`brand`**: Бренди (наприклад: 'Start', 'Start Pro', 'Lior').
- **`product`** та `product_translation`: Головна сутність товару (базовий опис).
- **`product_variation`**: Конкретні SKU товару. Наприклад, один `product` (Порошок) може мати різні `product_variation` (Пачка 1кг, Пачка 3кг). Всі ціни та залишки зберігаються саме тут!
- **`product_image`**: Фотографії для товарів та їх варіацій.
- **`product_review`**: Відгуки до продуктів з оцінкою (1-5).
- **`badge`** та `product_badge`: Бейджі для товарів (напр. "Хіт", "Новинка").

### 3. Атрибути та Характеристики
- **`attribute`** та `attribute_translation`: Довідник можливих характеристик (наприклад, "Призначення", "Вага").
- **`attribute_value`**: Значення атрибута для конкретного товару чи варіації.
- **`unit`**: Одиниці виміру (шт, грами, мл).

### 4. Комерція та Замовлення
- **`cart`** та `cart_item`: Кошик покупця. Кошик підтримує як зареєстрованих юзерів (`user_id`), так і анонімномих гостей через куки (`session_id`).
- **`wishlist`**: Список бажаного.
- **`order_status`**: Можливі статуси замовлень (дозволяє локалізувати статуси для клієнта).
- **`order`** та `order_item`: Основний зліпок замовлень. `order_item` копіює ціну на момент покупки, щоб майбутня зміна цін не зламала історію.
- **`delivery`**: Статус доставки (Нова пошта/Укрпошта, деталі ТТН).
- **`payment`**: Дані про транзакції (наприклад LiqPay: суми, статуси 'SUCCESS'/'FAILED').

### 5. Локалізація (Довідник)
- **`language`**: Доступні мови (наприклад 'uk', 'en').

## Робота з міграціями (CLI)

Для керування структурою використовується наша внутрішня обгортка над пакетом `golang-migrate`, яка знаходиться в `cmd/migrate/main.go`. Всі SQL-файли лежать у папці `migrations/`.

> [!NOTE]
> Перед початком роботи переконайтеся, що ваш файл `.env` містить коректну змінну `DATABASE_URL` (наприклад, `DATABASE_URL="postgres://user:pass@localhost:5432/dbname?sslmode=disable"`).

### 1. Накотити міграції (Up)

Щоб застосувати **всі доступні нові міграції**, виконайте:
```bash
go run cmd/migrate/main.go up
```

Якщо ви розробляєте нову фічу (наприклад, щойно написали `000003_add_banners.up.sql`) і хочете частково її накатити на 1 крок вперед:
```bash
go run cmd/migrate/main.go up 1
```

### 2. Відкотити міграції (Down)

Часто у розробці трапляється, що треба "переробити" останню таблицю. Команда `down` за замовчуванням **відкочує ТІЛЬКИ ОДИН КРОК (останню міграцію):**

```bash
go run cmd/migrate/main.go down
```
*(Це еквівалентно запуску `go run cmd/migrate/main.go down 1`)*

Якщо вам потрібно відкотити **всі** таблиці бази (тобто очистити її повністю для `init_schema`):
```bash
go run cmd/migrate/main.go down all
```

> [!WARNING]
> Будьте надзвичайно обережні з командою `down all` на продуктивному середовищі (Production), оскільки її виклик безповоротно ВИДАЛИТЬ усі дані (через `DROP TABLE`). З метою безпеки, за замовчуванням відкочується тільки одна остання міграція.

### 3. Таблиця `schema_migrations`
Бібліотека автоматично створює службову таблицю `schema_migrations` рівно з двома полями: `version` та `dirty`.
- Вона запам'ятовує останній порядковий номер успішно застосованого файлу міграції (наприклад, `version: 2`).
- **Ніколи не видаляйте її вручну**, інакше скрипт "забуде", що він вже створив таблиці, і спробує зробити `up` з самого початку (і впаде з помилкою "relation already exists").

### 4. Як створювати нові міграції
Якщо ви хочете змінити БД, дотримуйтесь цього формату:
1. Завжди створюйте пару файлів `.up.sql` та `.down.sql`.
2. Назва файлу має починатися з лічильника з провідними нулями:
   - `000003_feature_name.up.sql`
   - `000003_feature_name.down.sql`
3. У `up.sql` пишіть `CREATE TABLE ...` або `ALTER TABLE ... ADD COLUMN ...`.
4. У `down.sql` пишіть чистий реверс ваших дій: `DROP TABLE ...` або `ALTER TABLE ... DROP COLUMN ...`.
