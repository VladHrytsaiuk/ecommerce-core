# Стратегія Тестування (AquaWheel Backend)

Для забезпечення стабільної та надійної роботи бекенду інтернет-магазину, в нашому проєкті застосовується 3-рівнева піраміда тестування. Кожен вид тестів має своє чітке місце, призначення та інструментарій.

---

## 1. Unit Тести (Модульне тестування)

**Для чого:** Перевірка "чистотої" бізнес-логіки. Тестування того, чи правильно сервіс калькулює знижки, чи правильно обробляє логіку паролів і т.д.
**Де зберігаються:** Поруч з файлами, які тестуються (наприклад, `internal/product/service_test.go`).
**Швидкість:** ⚡️ Блискавично швидко (мілісекунди).

### Як це працює?
Модульні тести **ніколи не підключаються до реальної бази даних**. Замість цього ми використовуємо **Моки (Mocks)**. Наприклад, коли ми тестуємо `OrderService.CreateOrder()`, він під капотом звернеться до фейкового (замоканого) `OrderRepository`, який просто поверне заздалегідь підготовану відповідь, дозволяючи нам перевірити саму логіку `Service` в ідеальних умовах.

- **Бібліотека:** `github.com/stretchr/testify` (пакети `assert` та `mock`).
- **Генерація моків:** Ми використовуємо консольну утиліту `mockery` для автоматичного створення фейкових реалізацій усіх інтерфейсів.

**Як оновити моки (якщо ви змінили якийсь Repository Interface):**
```bash
mockery --all --keeptree
```

**Як запустити Unit-тести:**
```bash
go test ./internal/... -short
```

## 2. Integration Тести (Інтеграційні)

**Для чого:** Перевірка того, що наші SQL-запити в `Repository` шарі написані правильно, таблиці створюються коректно, а `FOREIGN KEY` не падають з помилкою.
**Де зберігаються:** Папка `tests/` або файли з суфіксом `_repo_test.go` в доменних блоках.
**Швидкість:** ⏳ Середня (займає кілька секунд на підйом бази).

### Як це працює?
Тут у гру вступає **Testcontainers + Docker**.
Замість фейків, кожен тестовий запуск автоматично:
1. Піднімає порожній ізольований контейнер Docker з PostgreSQL.
2. Накатує туди всі наші міграції (файли з папки `migrations/`, щоб створити всі 28 таблиць).
3. Зберігає туди тестові дані (наприклад, додає юзера в таблицю `user`).
4. Викликає ваш `UserRepo.GetByID()`.
5. Після завершення тесту повністю видаляє (знищує) Docker-контейнер, не залишаючи слідів (Clean Slate).

Ви ніколи не повинні вручну створювати/очищати БД для локального тестування — `Testcontainers` робить це автоматично!

**Як запустити Integration-тести:**
```bash
go test ./tests/integration/... 
# або виключно по всьому проєкту
go test ./... 
```

## 3. E2E Тести (End-to-End / API Тестування)

**Для чого:** Повна симуляція запитів від клієнтського Frontend-у або мобільного додатку. Робота всього ланцюга: від HTTP Middleware до Бази Даних і назад.
**Де зберігаються:** Папка `tests/e2e/`.
**Швидкість:** 🧱 Повільніше, через імітацію мережі та повного HTTP стеку.

### Як це працює?
1. В тестах використовується стандартний Go-пакет `net/http/httptest`.
2. Тест створює повний інстанс `Gin Router` зі всіма `Middleware` (Cors, Auth).
3. База Даних знову ж таки піднімається через `Testcontainers`.
4. Тест відправляє сире JSON тіло запиту на віртуальний сервер.
5. Тест "ловить" JSON відповідь і перевіряє, чи правильно повернувся статус-код `200 OK` або `400 Bad Request`, чи коректна структура JSON у відповіді.

Цей тип тестів гарантує, що рефакторинг не зламав "контракт" між бекендом та фронтендом.

---

## 🚀 Корисні команди для тестування

**Запустити всі тести у проєкті:**
```bash
go test ./... -v
```

**Перевірити покриття коду тестами (Coverage):**
```bash
go test ./... -coverprofile=coverage.out
go tool cover -html=coverage.out
```
*(остання команда відкриє красивий візуальний звіт у вашому браузері з підсвічуванням червоним кольором тих рядків коду, які ще не вкриті тестами)*.
