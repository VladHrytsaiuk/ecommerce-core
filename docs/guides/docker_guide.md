# 🐳 Docker Guide: Як працює наш Docker‑контейнер, чому він важить 82 MB та як його перезібрати

Цей гайд описує:

- Як влаштований наш `Dockerfile` (build‑stage vs runtime).
- Чому образ вийшов ~82 MB, а не “тяжіле” Go‑image з усім SDK.
- Як перезібрати образ для локального запуску через `docker-compose`.

***

## Як влаштований наш Dockerfile

Наш образ побудований за принципом **multi‑stage build**:

1. **Етап збірки** — повна Go‑сфера.
2. **Етап запуску** — мінімальний Alpine без нічого зайвого.

### 1. Етап збірки (Builder)

```dockerfile
FROM golang:1.25.4-alpine AS builder

WORKDIR /app

# Копіюємо файли залежностей (це прискорює наступні збірки)
COPY go.mod go.sum ./
RUN go mod download

# Копіюємо весь код
COPY . .

# Збираємо бінарник. CGO_ENABLED=0 робить його статичним (працює всюди)
RUN CGO_ENABLED=0 GOOS=linux go build -o main ./cmd/api/main.go
```

- `golang:1.25.4-alpine` — повне Go-середовище для збірки.
- Ми **спочатку копіюємо** `go.mod/go.sum`, щоб в Docker‑лайєрі не перекомпілювалися залежності кожного разу.
- Бінарник збирається статичним (`CGO_ENABLED=0`), тому не вимагає додаткових бібліотек у runtime‑оточенні.

### 2. Етап запуску (Final Image)

```dockerfile
FROM alpine:latest
WORKDIR /root/

# Копіюємо тільки готовий файл з попереднього етапу
COPY --from=builder /app/main .
# Копіюємо .env, щоб програма бачила DB_URL локально
COPY --from=builder /app/.env .

EXPOSE 8080

CMD ["./main"]
```

- `alpine:latest` — мінімальний Linux‑дистрибутив.
- До фінального образу потрапляє **тільки готовий бінарник `main` та `.env`**.
- Ніякого `go`‑SDK, компілятора чи GOROOT не копіюється.

Тобто:

- **Builder‑етап** — 100% для збірки.
- **Final‑етап** — тільки для запуску.

***

## Чому образ важить ~82 MB?

Образ вийшов відносно малим, тому що:

- Ми використовуємо **Alpine Linux** замість Ubuntu/Debian.
- У фінальному образі:
    - немає `golang` SDK;
    - немає `go`‑toolchain;
    - немає додаткових пакетів окрім мінімального ядра Alpine;
    - є лише:
        - статичний Go‑бінарник;
        - налаштування з `.env`.

82 MB відповідає:

- Розмір Alpine‑базового образу;
- Розмір компільованої Go‑програми з усіма імпортами (Gin, GORM, Zap тощо).

Це “чесно” для мінімального Про‑дакшен‑сумісного образу з Go‑бекендом.

## Як перезібрати Docker‑образ

Щоб **принудово перезібрати** образ та застосувати зміни з `Dockerfile` та коду:

### 1. Переконайтеся, що Docker‑демон працює

```bash
docker info
```

### 2. Перезібрати образ через `docker-compose`

У корені проекту виконай:

```bash
docker-compose build
```

Якщо потрібно **принудово перезібрати з нуля** (без кешу лайєрів):

```bash
docker-compose build --no-cache
```

### 3. Запустити (з перезібраним образом)

```bash
docker-compose up
```

або з rebuild‑флагом:

```bash
docker-compose up --build
```

Після цього `aquawheel-api` використовує **новий зібраний образ**.

Щоб подивитися, що саме займає місце:

```bash

```

або уважніше за іменем послуги:

```bash

```

Зазвичай ви побачите щось на кшталт:

```text

aquawheel-store_api         latest    82.3MB
```

***

## Як оновити/відняти щось, щоб ще більше зменшити образ

Якщо треба дещо оптимізувати:

- Перевір, чи в `.dockerignore` немає зайвих файлів (наприклад, `docs/`, `tests/`, `.git`).
- Можна видалити `.env` із фінального образу та пробросити його через `docker-compose env_file` (він already використовується).
- Можна зробити ще легший образ через `distroless` (Google), але Alpine + статичний бінарник вже дуже хороші.

***

## Як перезібрати образ, якщо змінюється `go.mod`/залежності

Якщо змінився `go.mod`/`go.sum`:

1. Виконай:

```bash
docker-compose build
```

2. Або, якщо хочеш принудово перезібрати залежності:

```bash
docker-compose build --no-cache
```

Docker перезібере лайєр з `go mod download` та перекомпілює бінарник, всі решта — як зазвичай.

***

## Коротко: команда для перезібрання образу

```bash
# З повторним використанням кешу (рекомендовано)
docker-compose build
docker-compose up

# Або все однією командою з rebuild
docker-compose up --build
```

Після цього ваш образ `aquawheel-api` буде **новим з усіма змінами з `Dockerfile` та коду**.
