# Git Flow & Правила Командної Роботи (AquaWheel)

У нашому проєкті використовується спрощений варіант **Git Flow** (без зайвої гілки `release`). Це гарантує стабільність робочого коду та легку взаємодію в команді.

## 📌 Основні гілки (Захищені)

У нас є дві головні гілки, у які **СУВОРО ЗАБОРОНЕНО** робити прямі коміти (`git push`). Усі зміни потрапляють туди виключно через **Pull Request (Merge Request)**.

- **`main`** 🟢 (Продакшен) — Це те, що клієнт бачить на "живому" сайті ПРЯМО ЗАРАЗ. Релізний код.
- **`develop`** 🟡 (Тестова/Наступний реліз) — Це те, що клієнт побачить у *наступному* оновленні. Сюди зливаються всі нові фічі від команди.

---

## 🛠 1. Старт нової задачі (Нова фіча)

Ти (або хтось із команди) береш задачу — наприклад, створення API для кошика.

> [!IMPORTANT]
> Усі нові задачі починаються **ТІЛЬКИ** з актуального стану `develop`.

```bash
# 1. Перемикаєшся у develop
git checkout develop

# 2. Обов'язково підтягуєш останні зміни від команди
git pull origin develop

# 3. Створюєш особисту гілку для своєї фічі
git checkout -b feature/cart-api
```

---

## 💻 2. Написання коду та Коміти

Ти працюєш локально, пишеш код, тестуєш і робиш коміти у свою гілку `feature/cart-api`. 
Намагайся називати коміти зрозуміло (використовуючи Conventional Commits).

```bash
git add .
git commit -m "feat: додав ендпоінт для додавання товару в кошик"
```

### Типи комітів (Conventional Commits)
Для того, щоб історія комітів була чистою та зрозумілою для всієї команди, ми використовуємо єдині префікси. Вони вказують, яка саме зміна була зроблена:

- **`feat:`** — розробка нової функціональності / фічі (напр., додавання нового сервісу або API-ендпоінту).
- **`fix:`** — виправлення багів і помилок (напр., обробка функції, що падала (крашилась)).
- **`docs:`** — оновлення документації (напр., зміни в README, Swagger чи `docs/`).
- **`test:`** — будь-які зміни, що стосуються тестового коду (напр., додавання Unit-тестів).
- **`refactor:`** — переписування (рефакторинг) коду без зміни бізнес-логіки системи (напр., виправлення після Code Review).
- **`style:`** — косметичні зміни (форматування, відступи, видалення зайвих пробілів чи коментарів). На саму систему не впливає.
- **`chore:`** — технічні/рутинні задачі, які не стосуються коду самого продукту (напр., оновлення `.gitignore`, лінтерів).
- **`build:`** — зміни в інструментах збірки та залежностях (напр., додавання/видалення пакетів у `go.mod`, Dockerfile).
- **`perf:`** — зміни, орієнтовані на оптимізацію продуктивності (напр., заміна складного циклу на більш швидкий).
- **`ci:`** — оновлення CI/CD скриптів чи пайплайнів (напр., GitHub Actions, GitLab CI).
- **`revert:`** — скасування змін попереднього коміту.

---

## 🚀 3. Відправка на сервер і створення Pull Request (PR)

Коли задача готова, ти відправляєш її на сервер (наприклад, у GitHub чи GitLab).

```bash
git push -u origin feature/cart-api
```

Після цього ти йдеш у веб-інтерфейс і створюєш **Pull Request**.

> [!WARNING]
> Ти маєш вказати правильний напрямок злиття (Target Branch):
> `feature/cart-api` ➡ `develop`
> **В жодному разі не в `main`!**

---

## 👀 4. Code Review та Злиття (Merge)

1. Команда або Tech Lead дивиться твій код.
2. Якщо все ок — натискають кнопку **Merge** (або Squash & Merge).
3. Твій код опиняється в `develop`.
4. Гілку `feature/cart-api` після цього **обов'язково видаляють**, щоб не засмічувати репозиторій "мертвими" гілками.

---

## 🚢 5. Реліз (Оновлення Продакшену)

Коли всі необхідні фічі (і від бекенду, і від фронтенду) злиті в `develop`, формується так званий поточний "Кандидат на реліз".

1. Ви розгортаєте гілку `develop` на тестовому сервері (Staging / Локально).
2. Ви перевіряєте, чи все працює разом стабільно і чи немає конфліктів логіки.
3. Якщо все супер — створюється Pull Request **напряму з `develop` у `main`**.
4. Після злиття (Merge) розширеної гілки в `main` — код відправляється (через CI/CD / розгортання) на реальний сервер до справжніх користувачів.

---

## 🚑 Що робити, якщо знайдено критичний баг на Продакшені? (Hotfix)

Уявімо критичну ситуацію: на живому сайті не працює оплата. Чекати до наступного повноцінного релізу з `develop` (де можуть бути сотні інших незавершених фіч) — не можна. Для цього використовується патерн `hotfix`.

> [!CAUTION]
> Гілка `hotfix` — це єдиний випадок, коли ми створюємо гілку від `main`, а не від `develop`!

1. Ти перемикаєшся на `main`, бо баг знаходиться саме там:
```bash
git checkout main
git pull origin main
```

2. Створюєш гілку для виправлення:
```bash
git checkout -b hotfix/payment-crash
```

3. Виправляєш баг, тестуєш, робиш коміт і пушиш:
```bash
git add .
git commit -m "fix: усунуто падіння при оплаті транзакцій"
git push -u origin hotfix/payment-crash
```

4. Створюєш PR з `hotfix/payment-crash` у `main` і мерджиш. Оновлення миттєво доїжджає на "живий" сервак. Користувачі врятовані.

> [!IMPORTANT]
> **КРИТИЧНО ВАЖЛИВИЙ КРОК (Синхронізація розробки)**
> Щоб цей же самий баг не "повернувся" і розробники не перезаписали виправлення під час чергового великого релізу з `develop`, ти ПОВИНЕН влити ці ж зміни в `develop`.
> 
> Після успішного злиття в `main`, обов'язково треба оновити й тестову гілку:
> ```bash
> git checkout develop
> git merge main 
> # Або відкрити ще один PR із main назад в develop у вебі.
> ```

---

## 📋 Коротке Резюме (Шпаргалка)

- 🟢 **`main`** — Наш продакшен. Те що бачать клієнти зараз.
- 🟡 **`develop`** — Наступна версія. Бачать розробники і тестувальники. Туди зливаються всі фічі.
- 🔵 **`feature/*`** — Гілка одного розробника для 1 задачі. *Відгалужується від `develop` ➡ зливається в `develop`*.
- 🔴 **`hotfix/*`** — Термінове виправлення бага. *Відгалужується від `main` ➡ зливається і в `main`, і в `develop`*.
- ⛔ **Табу** — Ніяких прямих `git push` в `main` чи `develop`. Всі працюють **ТІЛЬКИ** через Pull Requests!
