# Архітектура Пошукової Системи Aquawheel

У цьому документі описано алгоритми, оптимізації та технічні рішення, застосовані при реалізації пошуку товарів.

## 1. Загальна філософія (Practice Overview)
Чи є нормальним такий підхід? **Так, це "золотий стандарт"** для середніх та великих e-commerce проєктів, які працюють на PostgreSQL. Замість впровадження складних окремих пошукових рушіїв (типу ElasticSearch), ми використовуємо потужність PostgreSQL. 
Це дозволяє отримувати результати за лічені мілісекунди (<50ms) без додаткових витрат на синхронізацію баз даних.

## 2. Глобальні оптимізації (Database Layer)

### PostgreSQL `pg_trgm` та GIN Індекси
Для текстового пошуку не використовується звичайний перебір рядків.
1. У базу встановлено розширення `pg_trgm`. Воно розбиває текст на тріграми (трійки літер). Наприклад, "шампунь" -> `шам`, `амп`, `мпу` і т.д.
2. Створено GIN індекси на колонках `product_translation.name` та `product_variation.sku`.
**Результат:** Замість повного сканування таблиці (`Seq Scan`), база миттєво знаходить потрібні рядки за індексом, навіть якщо текст шукається в середині слова (`%запит%`).

## 3. Крос-мовний пошук (Multi-language matching)

### Проблема
Користувач може бути на англійській версії сайту, але ввести пошуковий запит українською (або навпаки). Також товар може тимчасово не мати англійського перекладу в базі.

### Алгоритм Вирішення
Замість жорсткої прив'язки пошуку до обраної мови інтерфейсу, система використовує конструкцію `EXISTS`:

```sql
WHERE EXISTS (
    SELECT 1 FROM product_translation pt 
    WHERE pt.product_id = product.id AND pt.name ILIKE '%запит%'
) OR product_variation.sku ILIKE '%запит%'
```
1. **Спектр пошуку:** База шукає збіг у ВСІХ перекладах назви товару, незалежно від поточної мови.
2. **Захист від дублікатів:** Використання `EXISTS` гарантує, що якщо товар підійшов по двох мовах одночасно, він все одно потрапить у фінальну видачу лише один раз (рядки не множаться).

## 4. Деталі реалізації ендпоінтів

### А. Швидкий пошук (Autocomplete) `GET /api/search/quick`
Створений для "випадайки" у хедері. Основна мета — максимальна швидкість та лаконічність.

**Алгоритм:**
1. **Унікалізація:** Застосовується `DISTINCT ON (p.id)`. Якщо у засобу є 5 об'ємів (варіацій), в автодоповнення потрапить лише ОДНА варіація (найдешевша), щоб не спамити однаковими товарами.
2. **Мовний Фолбек (Fallback):** Використовується подвійний `LEFT JOIN`:
   ```sql
   LEFT JOIN pt ON pt.lang = 'обрана_мова'
   LEFT JOIN pt_fallback ON pt_fallback.lang = 'uk'
   ```
   В поле `name` потрапляє результат `COALESCE(pt.name, pt_fallback.name)`. Це гарантує, що якщо перекладу обраною мовою немає, користувач все одно побачить українську назву, а не порожній рядок.
3. **Сортування:**
   - Пріоритет 1: Товари, чия назва ПОЧИНАЄТЬСЯ з пошукового запиту (Relevance Boost).
   - Пріоритет 2: Алфавітний порядок.
4. **Ліміт:** За замовчуванням повертає топ-5 результатів.

### Б. Повний пошук (Каталог) `GET /api/products?q=запит`
Використовується, коли користувач натиснув Enter або перейшов на сторінку результатів.

**Алгоритм:**
1. Працює як розширення існуючого каталогу. Це дозволяє поєднувати пошук з фільтрами (ціна, бренд, атрибути).
2. Повертає ВАРІАЦІЇ товарів. Кожна варіація (напр. об'єм 500мл та 1л) — це окрема картка товару в каталозі, бо клієнт шукає конкретний товар для покупки.
3. Якщо клієнт не обрав власне сортування (наприклад, від дешевих до дорогих), система автоматично застосовує динамічне ранжування:
   ```go
   // Пріоритет спочатку тим, хто починається з префіксу запиту
   ORDER BY (EXISTS (pt_boost WHERE name ILIKE 'запит%')) DESC, created_at DESC
   ```

## 5. Валідація запитів
На рівні Golang впроваджено захист від перевантаження бази порожніми запитами.
Застосовано `utf8.RuneCountInString(q) < 3`.
Це критично для кирилиці, адже `len()` у Go рахує БАЙТИ, а українські літери займають 2 байти. Правильна валідація коректно вимагає саме 3 повноцінних літери перед запуском запиту до бази.
