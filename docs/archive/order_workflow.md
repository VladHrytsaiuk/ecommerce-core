# 🛒 Архітектура та Життєвий Цикл Замовлень (Order Workflow)

Цей документ детально описує логіку обробки замовлень в AquaWheel Store: від наповнення кошика до фінального підтвердження оплати, включаючи сценарії для гостей, механізми безпеки та майбутні інтеграції.

---

## 👤 1. Ідентифікація Користувача (Authentication Modes)

Система підтримує два режими оформлення замовлення:

### Режим А: Авторизований клієнт
*   Користувач має активну сесію (JWT Access Token).
*   Бекенд автоматично використовує `user_id` з контексту запиту.
*   Адреси доставки можуть підтягуватися зі збереженого профілю.

### Режим Б: Гість (Silent Registration Flow) — БЕЗПЕКА 🔐
Якщо користувач не залогінений, система діє за наступним алгоритмом:
1.  **Ввід Даних:** Клієнт вказує Email, ПІБ та Номер Телефону.
2.  **Перевірка Email:** 
    *   Якщо такий Email **вже є** в БД: замовлення прикріплюється до існуючого `user_id` (в майбутньому тут може бути вимога підтвердити право володіння).
    *   Якщо Email **новий**: Система тихо створює новий запис `User` в БД.
3.  **Генерація Пароля:** Для нового користувача генерується безпечний криптографічний пароль. Пароль хешується, записується в БД і **НІКОМУ не передається** (ні в API, ні в Листі).
4.  **Вхід в акаунт:** Для майбутнього входу клієнт використовує стандартний функціонал "Забув пароль", де скидання йде через його Email.
5.  **Повідомлення на UI:** Фронтенд повідомляє клієнту, що для нього створено акаунт, і він зможе скористатися ним пізніше.

## 📱 2. Механізм Майбутньої Верифікації Телефону (Proof-of-Verification)

Щоб уникнути спам-замовлень, архітектура розрахована на Stateless OTP перевірку без передчасного створення користувачів:

1.  **Запит SMS:** Гість вводить номер -> тисне кнопку "Підтвердити" -> POST `/api/auth/verify-phone/request`. Бекенд зберігає `VerifyCode` у таблиці, де `target = "+380..."`, а `user_id = NULL`.
2.  **Підтвердження:** Гість вводить 4/6 цифр -> POST `/api/auth/verify-phone/confirm`.
3.  **Proof Token:** При успіху бекенд повертає короткоживучий (напр. 10 хв) підписаний **JWT токен**, який містить: `{ "phone": "+380...", "verified": true }`.
4.  **Чекаут:** Фронтенд розблоковує кнопку "Оформити". При натисканні у payload `POST /api/orders` додається поле `verification_token`.
5.  **Валідація:** Бекенд валідує підпис токена. Якщо валідний — замовлення створюється. **Стан (Session) на сервері не зберігається.**

## 🔄 3. Повний Життєвий Цикл Замовлення (Step-by-Step)

### Крок 1: Ініціалізація (POST `/api/orders`)
1.  Зчитування поточного Кошика клієнта (за `user_id` або `session_id`).
2.  Калькуляція фінальної суми (Items + можливі знижки).
3.  Ідентифікація/створення користувача (див. п. 1).
4.  **Атомарна транзакція в БД:**
    *   Створення запису в `order` з генерацією `order_number` (починаючи з 10000).
    *   Створення записів в `order_item` (копіювання актуальних цін на момент покупки!).
    *   Створення запису в `delivery` (інформація про обране відділення).
    *   Створення порожнього запису в `payment` зі статусом `pending`.
5.  **Очищення Кошика.**
6.  Повернення ID замовлення та Ready-статусу.

### Крок 2: Оплата (Bridge to Payment)
1.  Фронтенд отримує підтвердження створення замовлення.
2.  Система ініціює перехід на платіжний шлюз (напр., LiqPay redirect).
3.  Замовлення перебуває в статусі `Pending Payment` (Очікує оплати).

### Крок 3: Callback / Webhook (Після оплати)
1.  LiqPay надсилає зашифрований POST-запит на наш сервер: `/api/webhooks/liqpay`.
2.  Бекенд розшифровує дані, валідує підпис банку.
3.  **Якщо Успішно:**
    *   Оновлюється запис `payment` (статус `SUCCESS`, transaction_id).
    *   Оновлюється статус замовлення `order` -> `PAID` (Оплачено).
    *   **Trigger Notifications:** Запуск асинхронної черги відправки імейлів.

## 📧 4. Система Сповіщень (Notifications)

Після успішної оплати (або створення, залежно від конфігурації) сервер відправляє 2 листи:

### Лист 1: Клієнту (Customer Email)
*   **Тема:** Ваше замовлення №100XX успішно оформлено!
*   **Зміст:** 
    *   Деталі замовлення (список товарів, формули типу `2 х 100 = 200 ₴`).
    *   Реквізити доставки.
    *   Інформація про статус.
    *   Нагадування, що деталі доступні в кабінеті (і якщо це новий юзер — інструкція, що вхід через "Забув пароль").

### Лист 2: Адміністратору (Admin Notification)
*   **Одержувач:** Email, що береться з ENV змінної конфігурації.
*   **Зміст:** Технічна виписка для менеджерів для негайного збору замовлення на складі.

---

## 📦 5. Управління Складом (Inventory Policy)

Згідно з поточними вимогами, система **НЕ виконує** операції автоматичного списання товарів (`stock_quantity` не зменшується). Облік залишків ведеться вручну або через зовнішню ERP систему, що мінімізує ризики блокування продажів через помилки синхронізації.
