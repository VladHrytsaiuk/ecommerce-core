# Система бейджів товарів (Product Badges)

Цей документ описує логіку роботи автоматичних та ручних бейджів у системі AquaWheel.

## 1. Типи бейджів

Система підтримує два типи бейджів:
- **Автоматичні (Computed)**: Розраховуються "на льоту" сервісом на основі бізнес-правил.
- **Ручні (Manual)**: Призначаються адміністратором конкретному товару або варіації через БД/Admin API.

### Поточні бейджі та їх пріоритети

| ID | Ключ | Тип | Логіка спрацювання | Конфігурація (.env) |
|:---|:---|:---|:---|:---|
| 1 | **Новинка** | Auto | `created_at` продукту < `BADGE_NEW_DAYS` | `BADGE_NEW_DAYS=7` |
| 2 | **Хіт продажів** | Auto | `reviews_count` >= `BADGE_BESTSELLER_THRESHOLD` | `BADGE_BESTSELLER_THRESHOLD=5` |
| 3 | **Знижка** | Auto | `old_price` > `price` (у варіації) | Автоматично |
| >3 | **Інші** | Manual | Призначаються вручну в адмінці | - |

---

## 2. Детальна логіка

### Новинка (ID 1)
Бейдж додається автоматично до будь-якого товару, який був створений нещодавно. Період "нового" товару налаштовується в днях.

### Хіт продажів (ID 2)
> [!NOTE]
> **Тимчасове рішення:** Поки в системі не реалізовано модуль замовлень, популярність розраховується на основі кількості підтверджених відгуків.

### Знижка (ID 3)
Цей бейдж формується динамічно для кожної варіації окремо. 
- **Текст**: Система автоматично розраховує % знижки та формує текст: `Знижка 15%` (UK) або `Sale 15%` (EN).
- **Пріоритет**: Якщо товару вручну призначено бейдж "Акція" (ID 3), автоматичний розрахунок % замінить ручну назву, щоб дані завжди були актуальними.

---

## 3. Об'єднання та Відображення (Merging Strategy)

Бейджі можуть бути призначені на трьох рівнях:
1. **Товар (Product level)**: Бейдж відображається для всіх варіацій цього товару (наприклад, "Новинка").
2. **Варіація (Variation level)**: Бейдж стосується тільки конкретної моделі/кольору (наприклад, "Знижка" тільки на синій колір).
3. **Автоматичні**: Додаються сервісом на основі даних.

**Правило дедуплікації:**
У фінальну відповідь API (Catalog Brief або Product Detail) потрапляє унікальний список бейджів. Якщо один і той самий ID призначено і вручну, і автоматично — автоматичний має пріоритет.

---

## 4. Що потрібно доробити (Roadmap)

На даний момент система має обмеження, пов'язані з відсутністю даних про реальні продажі.

### Майбутні вдосконалення:

1. **Хіт продажів (Orders Integration)**:
   - Замінити `reviews_count` на `order_count`.
   - Додати логіку **періоду**: "Хіт за останні 7 днів" (вимагає SQL-запиту до таблиці замовлень з фільтрацією по даті).
   - Налаштування порогу продажів через `.env`.

2. **Рекомендуємо (Recommendation Engine)**:
   - Зараз ID 4 зарезервовано. В майбутньому бейдж має з'являтися на основі:
     - Переглядів користувача (через аналітику).
     - Подібних товарів, які купують інші.

3. **Лімітована серія (Stock Threshold)**:
   - Автоматичний бейдж, якщо залишок товару (`quantity_value`) менше певного порогу (наприклад, залишилося менше 3 шт).

---

## 5. Технічна конфігурація (.env)

```bash
# Кількість днів, протягом яких товар вважається новим
BADGE_NEW_DAYS=7

# Поріг відгуків (пізніше - продажів) для бейджа "Хіт"
BADGE_BESTSELLER_THRESHOLD=5
```
